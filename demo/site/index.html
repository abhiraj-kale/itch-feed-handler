Read the bytes where they land

Every ITCH message is a fixed-size big-endian record. The parser never copies or converts a message up front: it hands the handler a pointer, and each field is decoded only when it is read. This is the most recent order message from the live feed above. Hover a field.

04 / Inside

From a UDP packet to a strategy

Two threads. The network thread owns the socket, the sequencing, the parser, and the books. Top-of-book changes go to the strategy thread through a lock-free ring, so a slow strategy can never stall the feed.

UDP socketmulticast join, 64 MB receive buffer
MoldUDP64 sessionsequence check, park future packets, request gaps
Zero-copy parserlength-prefixed views, switch on type
Book builderorder table + per-symbol levels
SPSC ringtop-of-book updates, never blocks
Strategy threadpinned to its own core

Gap recovery

Each packet carries the sequence number of its first message. A packet from the future is parked, the missing range is requested from the retransmission server, and parked packets are released the moment the hole is filled. Duplicates and overlaps are trimmed message by message.

Prefetching ahead

The order table is the one structure too big for cache. The parser looks 8 messages ahead and prefetches the hash slot each upcoming execute, cancel, delete, or replace will touch, so the memory fetch overlaps with useful work.

Flat order table

Live orders sit inline in an open-addressing table keyed by order reference: 24-byte records, linear probing, and backward-shift deletion so constant add and delete churn never leaves tombstones behind.

Levels with the best at the back

Each side of each book is a sorted vector with the best price last. Most updates land within a few levels of the touch, and a level that empties below the touch is kept for reuse instead of shifting the vector.

Checked against a reference, symbol by symbol

Tests replay 900k messages through the book builder and a plain std::map book and compare the full depth of every symbol. Another test feeds MoldUDP64 packets with loss, duplicates, reordering, and a retransmission server that also loses answers, and requires every message delivered exactly once, in order. End to end over real UDP multicast, the book rebuilt from a feed with 0.5% packet loss matches the book built from the file.
